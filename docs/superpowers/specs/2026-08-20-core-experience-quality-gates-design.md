# 核心体验质量门禁设计

日期：2026-08-20

状态：已完成对话设计确认，等待用户审核书面规格

## 背景

仓库整理、现有测试、发布边界和线上视觉同步已经完成。下一轮迭代优先建立可重复、可阻断回退的核心体验质量基线，而不是继续扩展功能或改版。

本设计覆盖性能、移动端、可访问性、SEO、交互稳定性和资源预算。目标是在保持线上视觉、内容结构、导航和公开 URL 不变的前提下，修复可测量问题，并把稳定检查接入 CI。

## 已确认决策

- 采用综合质量基线，不单独偏向性能、SEO 或可访问性。
- 首批覆盖 5 条核心路径，并同时验证桌面端和移动端。
- 保持现有线上视觉与信息架构，只允许为质量修复进行必要的细微调整。
- 采用分层质量门禁：确定性静态检查、真实浏览器体验检查和多次性能采样。
- 质量门禁长期保留并进入 CI。
- 现有 `pnpm run check` 保持快速、确定性；新增完整浏览器命令 `pnpm run check:quality`。

## 目标

1. 为核心页面建立可复现的质量基线和明确阈值。
2. 发现并关闭所有 P0、P1 核心体验问题。
3. 为每项修复增加自动回归检查。
4. 阻止性能、可访问性、SEO、移动端和交互质量回退。
5. 生成可定位失败原因的报告、截图和 trace。
6. 保持现有公开契约和主要视觉不变。

## 非目标

本轮不包含：

- 案例筛选或标签功能。
- 页面反馈、用户统计或新的分析平台。
- 大规模内容扩写或 269 张待替换图片的系统性替换。
- 首页、帮助页或小白书的明显视觉改版。
- Git 历史重写。
- 与质量问题无关的组件重构。

## 覆盖范围

### 核心路径

- `/`
- `/wb-x/`
- `/resources/`
- `/help/`
- `/wb-x/reading-guide/`

旧路径兼容仍由现有构建和发布边界检查负责。本轮不得破坏 `/bluebook/`、`/reading-guide` 和 `/guide/reading-guide` 的兼容页面、canonical 或跳转行为。

### 视口

- 桌面端：`1440 × 900`
- 移动端：`390 × 844`

### 允许的实现变化

- 语义标签、ARIA、图片 `alt`、图片宽高。
- 键盘行为和焦点可见性。
- 对比度、细微间距和移动端溢出修复。
- `prefers-reduced-motion` 支持。
- 图片、字体、CSS 和 JavaScript 的加载策略。
- 按页面或功能拆分大型客户端依赖。

任何影响主要排版、文案层级、导航结构、CTA 目标或公开 URL 的变化都超出本规格，需要单独设计确认。

## 总体架构

质量系统分为三层。

### 1. 静态契约层

静态层读取源码、生产构建输出和资源清单，执行快速、确定性的检查：

- 核心路径构建产物存在。
- 页面标题、描述、canonical 和单一 H1 满足契约。
- 主要语义区域和必要导航存在。
- 内容图片具有适当的 `alt`；需要参与布局的图片具有宽高。
- 公开资源、本地链接和旧路径兼容保持有效。
- JS、CSS、字体和首屏图片符合资源预算。
- 生产构建不再产生大于 500 kB chunk 的警告。

静态层不得依赖网络、浏览器时序或外部服务。

### 2. 浏览器体验层

浏览器层使用生产构建，对 5 条路径和 2 个视口执行矩阵检查：

- 自动可访问性扫描。
- 键盘可达性和焦点可见性。
- 主要导航、CTA 和关键交互。
- 横向溢出。
- 页面控制台错误。
- URL、标题和关键页面标记。
- `prefers-reduced-motion` 下的行为。

浏览器层使用 Playwright 和 axe。依赖仅作为开发依赖，不进入生产运行时。

### 3. 真实性能层

性能层对生产构建运行 Lighthouse。每个路径和视口运行 3 次，以中位数作为阻断依据。单次异常不得单独导致失败。

CI 中不依赖不稳定的第三方网络响应。已知分析端点可以在审计时阻断，但脚本存在、加载方式和静态体积仍受静态契约和资源预算约束。报告必须明确记录被阻断的第三方端点，不能静默忽略。

## 指标与阻断规则

### 确定性硬门禁

- 5 条核心路径均能构建并返回正确页面。
- canonical、公开 URL 和旧路径兼容不回退。
- 每页具备唯一标题、描述、单一 H1 和合理语义区域。
- 自动可访问性扫描无 `critical` 或 `serious` 问题。
- 键盘可以到达主要导航、CTA 和交互控件。
- 焦点状态清晰可见。
- 桌面端和移动端横向溢出均为 0。
- 页面控制台错误为 0。
- 核心链接和交互目标正确。
- 动画尊重 `prefers-reduced-motion`。
- 构建无大于 500 kB chunk 的警告。

### 性能与质量阈值

每个路径、每个视口使用 3 次运行的中位数：

- Performance：桌面端不低于 90，移动端不低于 80。
- Accessibility：不低于 95。
- SEO：不低于 95。
- Best Practices：不低于 95。
- LCP：不高于 2.5 秒。
- CLS：不高于 0.1。
- TBT：不高于 200 毫秒。

### 资源预算

实施阶段首先记录批准前基线，然后提交 `quality-budget.json`。该文件至少包含：

- 每条核心路径的初始 JavaScript 体积。
- 共享和页面 CSS 体积。
- 字体总体积。
- 首屏图片总体积。
- 单个最大 chunk 的压缩前体积。

完成修复后的批准值成为正式预算。后续任一类别不得增长超过 2%，且单个 chunk 不得再次超过 500 kB。普通检查命令不得自动更新预算。

### 例外

例外必须显式记录：

- 失败规则或指标。
- 原因和用户影响。
- 负责人。
- 补救措施。
- 不超过 30 天的到期日。

第三方资源失败优先通过隔离、延迟或移除解决，不得直接降低全局阈值。到期例外自动成为 CI 失败。

## 文件与组件边界

预期新增或调整以下边界，具体文件拆分由实施计划确定：

- `scripts/quality/`：核心路由配置、静态审计、预算比较、预览编排和报告汇总。
- `tests/quality/` 或现有测试目录中的质量契约：验证审计器本身和确定性规则。
- Playwright 配置与核心路由浏览器测试。
- Lighthouse CI 配置。
- `quality-budget.json`：批准的预算和阈值。
- `audit/quality/`：需要长期保留的摘要、对比图和人工复核证据。

Playwright 浏览器、Lighthouse 原始缓存、trace、临时截图和运行产物必须进入忽略规则。只有有复核价值的最终报告和精选证据进入 `audit/quality/`。

## 命令与 CI

### 本地命令

- `pnpm run check`：保留现有单元测试、仓库卫生、链接、资源和构建检查。
- `pnpm run check:quality`：执行生产构建、静态质量检查、浏览器矩阵、Lighthouse、预算比较和报告汇总。

`check:quality` 使用 Node 编排器：

1. 验证生产构建存在或先构建。
2. 在回环地址上选择可用端口并启动临时预览。
3. 等待可验证的 HTTP 就绪条件。
4. 运行静态契约检查。
5. 运行 Playwright 双视口矩阵。
6. 运行 Lighthouse 三次采样。
7. 比较资源预算并生成汇总报告。
8. 无论成功或失败都关闭预览进程。

### CI

CI 必须：

1. 使用仓库固定的 Node 和 pnpm 版本安装依赖。
2. 安装与 Playwright 版本匹配的 Chromium。
3. 运行 `pnpm run check`。
4. 运行 `pnpm run check:quality`。
5. 失败时上传 Lighthouse 报告、Playwright trace、失败截图和汇总 JSON。

质量浏览器依赖不得加入生产 dependencies，也不得增加公开页面运行时代码。

## 错误处理与诊断

- 任一阶段失败都返回非零退出码。
- 预览进程必须在 `finally` 路径关闭，不能残留端口或子进程。
- 失败信息必须包含路径、视口、规则、预期值、实际值和证据位置。
- 工具启动失败、浏览器安装失败和页面质量失败使用不同错误分类。
- Lighthouse 单次异常保留在报告中，但只用中位数阻断。
- 报告生成失败不能掩盖原始质量失败。
- 预算文件解析错误或过期例外直接阻断。

## 实施阶段

### 阶段 1：建立真实基线

在不修改页面实现的前提下运行三层审计，保存核心矩阵的现状指标和必要证据。发现按以下级别分类：

- P0：页面不可用、导航错误、严重可访问性或公开 URL 问题。
- P1：未达到本规格硬门禁或质量阈值。
- P2：不阻断本轮交付，但有明确后续价值。

### 阶段 2：确定性问题修复

优先修复语义、SEO、图片尺寸、键盘、焦点、对比度、溢出、控制台和 reduced-motion 问题。每个问题先增加能失败的检查，再修改实现。

### 阶段 3：性能优化

只处理基线证明确实影响核心路径的项目，候选包括：

- 延迟加载非首屏内容。
- 按页面拆分 Mermaid 或其他大型依赖。
- 优化图片和字体策略。
- 减少不必要的客户端 JavaScript。
- 移除或延迟不必要的第三方请求。

不得为提高分数进行无证据重构，不得降低视觉质量或删除必要功能。

### 阶段 4：门禁和最终验收

把稳定检查接入 CI，运行全部现有和新增检查，复核线上与本地的视觉、文案、链接、公开 URL 和核心交互，并生成修复前后报告。

## 测试策略

- 审计脚本使用单元测试覆盖通过、失败、边界和错误分类。
- 每项页面修复遵循先失败、后通过的回归测试流程。
- 浏览器测试以语义定位器为主，不依赖脆弱坐标或源码顺序。
- 性能测试使用生产构建，不使用开发服务器。
- 资源预算比较测试覆盖增长阈值、缺失记录、非法数据和过期例外。
- CI 编排测试覆盖预览启动失败、超时、子进程失败和清理路径。
- 最终运行现有 `pnpm run check`，不得减少现有测试覆盖。

## 最终验收

本轮只有同时满足以下条件才可完成：

- 所有 P0、P1 项关闭。
- 5 条路径、2 个视口的静态和浏览器硬门禁通过。
- Performance、Accessibility、SEO、Best Practices、LCP、CLS 和 TBT 达到阈值。
- 资源预算通过且不再出现大于 500 kB chunk 警告。
- 原有 374 项测试和全部新增测试通过。
- `pnpm run check` 与 `pnpm run check:quality` 均通过。
- 线上与本地的主要视觉、文案、导航、CTA、公开 URL 和旧路径兼容没有未经批准的偏差。
- 最终报告记录修复前后指标、剩余 P2、正式预算和所有未到期例外。
- 本地生产预览保留供用户验收。

## 风险与控制

- **性能分数波动**：每个样本运行 3 次并使用中位数；确定性预算独立阻断。
- **浏览器依赖增加 CI 时间**：复用同一 Chromium 安装，保持 `pnpm run check` 为快速本地命令。
- **第三方网络不稳定**：审计中显式阻断已知端点并单独记录，静态检查仍约束其接入方式。
- **为了指标破坏视觉**：最终必须进行线上与本地双视口对照，视觉变化受已确认边界约束。
- **审计工具自身错误**：审计器有单元测试，并区分工具失败与页面失败。
- **范围膨胀**：P2 项记录到后续清单，不在本轮无边界扩展。

## 后续工作

本规格经用户审核后，下一步使用 `superpowers:writing-plans` 编写逐任务实施计划。实施计划应先建立基线和审计工具，再根据真实结果安排修复，不得预先假设具体页面缺陷。
